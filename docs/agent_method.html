What this document is

The framework, and its realization

We wrote a statistical proposal for this task. This deck restates it and marks, for each part, what version 2.8 implements, what it simplifies, and what stays open.

The 200 public examples and the local evaluator are development feedback. They are not the objective. The objective is to turn our informal recommendation reasoning into variables and equations that can be measured, adjusted, and tested.

Catalogue: 50,000 fixed clothing, shoes and jewellery items. The agent recommends only from it.

Core design principle

History is a bounded prior, not the answer

Use history to improve the probability over plausible targets, but never spend so much personalization risk that an unresolved historical assumption removes an otherwise plausible product.

Correct history can improve early ranking. Conflicting history can push the target out of the top ten. So history earns ranking priority at most — never candidate exclusivity.

Version 2.8 takes this to its limit: historical preference influences only which question to ask. It has no vote in the ranking, so it cannot remove a candidate.

Version 2.8.4 removes that too. The question policy no longer reads the profile — history now enters the agent at no point.

Statistical problem definition

A belief that updates each turn

Required information is revealed turn by turn, and stated preferences may later be revised. We treat the task as a sequential decision under time-varying evidence.

Pt(p) = P( target = p | E1:t , H , C )

p product  ·  t turn  ·  E1:t evidence so far  ·  H historical preference  ·  C catalogue evidence

actiont = ( Top-10t , questiont )

Version 2.8 represents this belief as a score and a ranking, not a normalized probability. Every turn still returns a full Top-10.

Product ranking equation

Which terms version 2.8 keeps

The proposal's ranking score has five terms. Version 2.8 uses three.

St(p) = SI + SC + ε SQ
SI  intent relevanceBM25 over the accumulated conversation, weight 1.00
SC  constraint satisfactionweight 1.35, per constraint 1.35 firm / 0.85 soft — a score term, not a filter
SQ  qualityweight 0.025 — a weak tie-breaker only

Two terms are left out on purpose:

  • λt SH — historical preference. No vote in the ranking, so it can never remove a candidate. Version 2.8 still used it to prioritise questions; version 2.8.4 drops that, and history enters nowhere.
  • SV — verified violation. A product is never penalised for metadata it simply does not state.

The agent · per-turn flow

Five steps, every turn

The loop ends when the target is found or after turn ten. The next five slides follow these labels.

The agent · step 1

1 · Update state

Considered here: is the new message a fresh constraint, a replacement of an earlier one, or an explicit "no preference"?

statet = Update( statet−1 , messaget )

Each attribute holds one of four states. A replacement does not delete the old value — it marks it SUPERSEDED and the new one ACTIVE. On an override, the shown-list memory is cleared and superseded values are restored: in this simulator the replaced value still points toward the target.

UNKNOWNnot mentioned yetNO_PREFERENCEcustomer has none
ACTIVEa live requirementSUPERSEDEDreplaced, but kept

Proposal's NEGATIVE state is dropped — the simulator produces no negative requirements (slide 12).

The agent · step 2

2 · Retrieve candidates

Considered here: which products could plausibly be the target? This step targets recall, not precision — the proposal separates the two.

  • Two BM25 passes over the catalogue text: one broad (category plus everything disclosed), one narrow (firm constraints only). The better score per product is kept.
  • A product that was a strong candidate on an earlier turn but not shown is carried forward at 0.78×. A previous miss is not a rejection.
  • A product already shown in the Top-10 is held out on later turns — it had its chance to convert. This hold-out is cleared when an intent override is detected, because a target shown before the override does not yet count as a hit.
  • No personalization enters retrieval.

The agent · step 3

3 · Score candidates

Considered here: the ranking equation from slide 5, with concrete weights.

St(p) = r + 1.35 Σ w · m + 0.025 Q

r — BM25 relevance, scaled to 0–1. m — fraction of a constraint's words found in the product text. w — 1.35 firm, 0.85 soft. Q — quality: 0.65 · rating/5 + 0.35 · log-scaled review count.

A constraint the product's metadata is silent on neither helps nor hurts it. Nothing is filtered out at this step — the proposal's hard filter becomes a soft term, so a candidate can only lose rank, never eligibility.

The agent · step 4

4 · Select Top-10

Considered here: how certain is the intent, and which attributes are still unresolved?

certainty = 0.16 · (active) + 0.18 · (firm) + 0.18 if category known
list value = score + 0.12 · (1 − certainty) · novelty

When certainty is high, take the ten highest scores. When it is low, give a small bonus to products that differ on the unresolved attributes — so one wrong assumption cannot fill all ten slots. High ranks stay score-driven, to protect MRR.

This is the proposal's Top-10 risk portfolio: exploitation plus coverage of unresolved hypotheses only — not generic diversity.

The agent · step 5

5 · Choose a question

Considered here: is there enough in the conversation to justify a specific question, or should the agent keep eliciting openly? Settled at version 2.8.4.

Turn one is always the open question, and it stays the default every turn after. A specific question that misses hands the choice straight back to it. No value-of-information search, no per-attribute prior, no profile.

Appendix E gives the full order of checks; Appendix C, the 700-session evidence for staying open.

Invariants

Held, and one open

Held: a full Top-10 every turn · a previous miss is not a rejection · explicit evidence dominates history · missing catalogue evidence is not a violation · the four states stay distinct · coverage protects only unresolved attributes · no scenario or generator logic anywhere.

Open. A product shown before an intent override is detected is held out by the no-repeat rule (step 2). If the override wording is not recognised, the target stays held out — on a held-out set with reworded overrides the override score falls from 0.80 to 0.24. Override detection and this hold-out are being revised together.

Appendix A · official scoring

How the evaluator scores a run

Per session: Hit = 1 if the target is in the returned top ten, else 0  ·  Reciprocal Rank = 1 / (rank of the target), or 0  ·  Turn = turn the target first appeared, or 11.

HR = Σ HitN   MRR = Σ RRN   MTTC = Σ TurnN   Efficiency = 11 − MTTC10
TechnicalScore = 0.50 HR + 0.30 MRR + 0.20 Efficiency

N = number of sessions. Efficiency is clipped to [0, 1]. Scenario breakdowns are for analysis; scenario labels are never agent inputs.

Appendix C · question policy

The open question dominates the simulator

Candidate slide · pending review

An instrumentation result and its reading. Not yet folded into the main deck.

Every question across the public set and both held-out sets — 700 sessions — was logged with the target's rank before and after the answer. Expected rank improvement per question, a target that fell out of the ranked list counted as rank 500:

expected rank gain per question asked
QuestionPublicHeld-out, familiarReworded overrides
open — "anything else?"+147+131+45
material+9−2−7
feature+14−48−17

The open question carries the turn. Every specific attribute question is net-neutral to negative on the held-out sets. Its returns also fall off fast — on the held-out set the 1st open question is worth about 180, the 2nd about 75, the 3rd about 15, the 4th and later nothing: the customer's constraint list is drained by the third turn.

An agent that only ever asks the open question scores 0.870 public, 0.848 held-out — above version 2.8.

The reading. The simulator discloses up to two constraints per open question, ungated by attribute. Its customer holds a complete pre-written intent list and reads it out on request — so a specific question can only reorder what the open question already returns. Open elicitation is near-optimal here because the customer is a cooperative oracle.

A real vague-intent shopper is not. Asked "anything else?", they have nothing more to give. The brief's Proactive Guidance pillar — detect an over-broad candidate pool, narrow it by structured clarification — targets that case, and the local evaluator cannot reward it.

Direction for part two: when the candidate pool stays broad after the constraint list is drained, switch from open elicitation to a discriminating question chosen to split the surviving candidates — a choice the shopper can answer with no prior preference. Not yet built.

Appendix D · code shape

The agent as modules

Constants, regexes, helper functions and the two dataclasses live in a shared starter/helper/ package. What remains in agent_v2_8_4_1.py is only the Agent class — retrieval, scoring, and the question policy.

Two deltas carried into the shared helpers: _OVERRIDE_RE gains three reset phrases (start over, scratch that, changed my mind); SessionState gains two sticky-depth fields. Both additive. The refactor is byte-identical to the flat build across 700 sessions.

deliberate exclusion

The language-model path is not an omission. Override detection stays on a regex so the agent runs offline and reproducibly — the final scoring box may disable network access.

Appendix E · question policy in full

The five checks, in order

Evaluated top to bottom each turn; the first match returns. Four of the five paths end at the open question.

  1. The open question has not been asked yet → open question (turn one).
  2. The last specific answer is still productive and that attribute is not exhausted → ask it again (sticky mining).
  3. The last turn was a specific question that yielded nothing → open question — hand the axis choice back.
  4. The last turn was not a productive open answer → open question.
  5. A single dimension gained two or more new pieces of evidence this turn, was never asked, and is not exhausted → score the eligible dimensions by _guarded_discrimination over the candidates and return the best one — a single refinement. Otherwise → open question.

The catalogue only prioritises and sanity-checks an already-eligible dimension in check 5; it never makes one eligible. Eligibility comes entirely from the conversation.
